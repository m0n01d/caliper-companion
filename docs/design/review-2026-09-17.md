# Design review — scale and spacing, 2026-09-17

Owner's note after the iPhone build: "some spacing and things feel off; the sizes of things feel
small, like the small pictures of the scanned faces." This is a layout-and-scale review inside the
existing system (DESIGN.md §2 tokens, §11 native feel: system type at the HIG scale, capsules,
inset grouped lists, 16 px margins, glass only in the bar). No re-theme.

Sources: the twelve screenshots in `docs/design/mockups/01…12-*.png` (390×844 @2x), `src/theme.css`,
`src/global.css`, the four page stylesheets and their `.res` views. Every number below is measured
from those. Fixes are marked **do now** (CSS/markup only, no layout decision needed) or **with the
layout change** (depends on the Part-page recommendation in §3).

## 2. Spacing scale audit

`--cc-space-1..6` = 4 / 8 / 12 / 16 / 20 / 24; `--cc-page-x` = 16 (§11.1). What the pages actually use:

| Where | Actual | On scale? | Note |
|---|---|---|---|
| Page margin, page top padding | 16 | space-4 / page-x | ✓ |
| Between sections (`.stack-lg`) | 20 | space-5 | Barely larger than in-section 12; the page reads as one column. Use **24 (space-6)**. |
| In section (`.stack`) | 12 | space-3 | ✓ |
| Group header → group | 8 | space-2 | ✓ |
| List row | 12 / 16 | space-3 / space-4 | ✓ |
| Faces row gap / slot label gap | 8 / 4 | space-2 / space-1 | ✓ |
| Features table cells | 9 / 10, outer 14 | **no** | §4's "9 px" predates §11; use 12 / 8, outer 16. |
| Warning row, `.page-error` | 10 / 14 | **no** | 12 / 16. |
| Text input | 8 / 14 | **no** (14) | 14 side padding is fine for inputs (matches the 12 px radius); keep, but it's the only place 14 should survive. |
| Chip | 0 / 14 | no | Capsules: 0 / 16 for 44 px, 0 / 14 for 40 px. |
| Pill | 6 / 12 | space-3 | ✓ |
| Capture view gap / slot row gap | 20 / 12 | space-5 / space-3 | ✓ |
| Annotate column gap, overlay inset | 12 / 8 | space-3 / space-2 | Overlay inset 12 would match the pill radius. |
| Annotate tools | gap 6, pad 2 4 | no | Goes away with A1. |
| Panel padding / kind row / actions | 16 / 12 / 8 | ✓ | |
| Segmented | pad 2, gap 4 | — | Fine (concentric). |

Verdict: the scale is respected for everything *except* the values that came from §4's pre-§11
component specs (9, 10, 14). **space-6 (24) is never used as a vertical rhythm step** — it only
appears as capsule side padding — so the top of the scale is dead and sections don't separate.
Two rules fix the rhythm: sections 24 apart, and 14 retired everywhere except input side padding.
Also stale: §3 still says the photo canvas is "350 at 390"; it's 358 since the margin became 16.

Faces as a 2-column grid of square **Face cards**: `(358 − 16) / 2 = 171 px` at 390 (156 at 360),

### C. Dense rows (`part-c.html`)
Each face is a full-width inset grouped row: 96 px square thumbnail (teal ring + 20 px check badge),
label Headline 17, "1600 × 1200 · 2 dimensions" Footnote, chevron; a final "Capture a face" row
(amber Body, dashed 96 px slot). Separators inset to the text edge at 124 px. Features table, Export,

### D. Segmented (`part-d.html`, optional)
A 44 px capsule segmented control "Faces · 3 | Features · 3" under the bar switches two full-height
panes (Faces = A's grid, Features = B's rows + warning row); Export is docked at the bottom of the
scroll container with `position: sticky` (opaque `cc-ground`, hairline top — never `fixed`, never
glass), the timer moves into the bar subtitle. **Optimises for** Export always being one tap away
and for long parts (the pane scrolls, the action doesn't). **Costs:** it defeats "glance": faces and
features are never on screen together, and for the common 3–4-face part both panes are
half-empty (the grid ends at y ≈ 480, the features at ≈ 415, Export at 782) — it *creates* the dead
space the owner is complaining about. A tab is also a new interaction and a new state to restore.
**Carries** to Capture as "Faces | Shoot" — no.

## 4. Recommendation

**A, Gallery-first.** It fixes the exact complaint with numbers — the face thumbnails go from 56 to
171 px (9.3× the area) and the four cards fill 358 × 358 px, so the photos the dimensions live on
become the screen's subject instead of a strip that is 37 % gutter. It keeps a 3–4-face part on one
screen (Export ends at y = 809 of 844, in the thumb zone) and it is HIG-native: a grid of navigable
cards over an inset grouped list, nothing new to learn. It costs the least of the four: no
"which face is the hero" rule (B), no 200 px scroll to reach the numbers (C), no tab state (D), and
at five or more faces it degrades gracefully to 3-up 109 px cards. The Face card is one component
that also replaces the Capture screen's chip row + slot row (tap a card to pick the kind, shutter
anchored under the grid, so the capture loop moves into the bottom 60 %) and the Parts row's empty
52 px square (72 px first-face thumb). Take B's Title 2 value column only if numbers must be
readable from arm's length; otherwise Body 17 keeps rows at 66 px and the page on one screen.
